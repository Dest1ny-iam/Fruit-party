# 水果切切乐第二轮迭代：UI 与需求分析

> 目的：让游戏从“功能可用”进入“用户愿意持续使用、运营可控、上线可验证”的状态。本文只定义需求与验收口径，不代表这些内容已经开发完成。

## 1. 当前基线与本轮边界

当前项目已有玩家认证、普通/困难/无尽模式、背包、商店、通知、个人主页、管理后台、SQLite 数据库、实时事件和 3D 水果资源管线。计分与结算应继续由服务端裁决，前端只展示已确认的状态。

第二轮以“统一体验 + 真实数据状态 + 上线质量”作为主线：

- 优化大厅、关卡、游戏、结算、个人页、商店和后台的视觉一致性。
- 补全加载、空数据、错误、禁用、网络中断和移动端等完整状态。
- 所有可见业务数据均从 API/数据库读取；前端不得再保留排行榜、余额、关卡状态或运营记录的演示数据。
- 不在本轮接入真实支付；充值仅保留明确标注的人工收款码流程与超时关闭。
- 真实水果模型尚未放入 `public/models`，因此不将临时几何体截图作为最终美术标准。

## 2. 三种视觉方向

| 方向 | 画面特征 | 适用性 | 风险 |
| --- | --- | --- | --- |
| A. 果汁市集 | 明亮果色、白色大面积留白、插画标签 | 亲子与轻度休闲感强 | 与现有深色游戏画面割裂，后台也容易显得玩具化 |
| B. 午夜果园（推荐） | 深黑蓝底、低饱和莓红/柑橘金/叶绿点缀、玻璃感极弱的深色表面 | 同时适配切水果的就不爽感、竞技分数和运营后台 | 需要控制高光，避免再出现刺眼的亮蓝或大面积渐变 |
| C. 竞技控制台 | 黑灰、信息密度高、强数值与排行榜中心化 | 适合深度挑战与后台 | 普通玩家会感觉偏硬，商店和个人页亲和力不足 |

### 推荐：B「午夜果园」

这套方案保留游戏已有的深色气质，但让每种水果色只承担一个明确用途，而不是整页混用：

- 背景：近黑 `#07111F`，次级表面 `#0D1B2A`，分隔线 `#22354A`。
- 主行动色：克制的柑橘金 `#E6A74A`，用于“开始、领取、确认”。
- 风险与困难模式：深石榴红 `#A94853`，只用于炸弹、失败、危险关卡和撤销。
- 成功与能量：叶绿 `#5FA67A`，用于通关、恢复、可用状态。
- 信息色：灰蓝 `#8195AA`，不用高饱和蓝色做大面积背景。
- 圆角：普通容器 `10px`，主按钮 `10px`，小图标按钮 `8px`；不再使用直角大框或过大的药丸按钮。
- 动效：只保留切中、炸弹、解锁、金币变化、弹窗出现五类反馈；均支持系统“减少动态效果”偏好。

后续视觉预览建议先做三张可对比的静态稿：大厅、关卡选择、个人主页。确定方向后，再逐页改真实页面，而不是只做一张无法落地的概念图。

## 3. P0：上线前必须补齐

### 3.1 真实数据与状态一致性

1. **单一数据源。** 用户名、头像、金币、能量、背包、关卡进度、最高分、通知、商品、权限与后台统计都只读 API 数据。前端允许短暂缓存，但缓存必须有版本、失效和刷新规则。
2. **统一请求状态。** 每个数据页必须有骨架加载、空状态、可重试错误状态；请求期间禁用会重复提交的按钮。
3. **实时同步边界。** 金币、能量、权限、禁用状态、通知未读数、商品配置与后台日志通过实时事件更新；断线后显示“正在重连”，重连成功后重新拉取当前页数据。
4. **服务端最终裁决。** 关卡开始扣能量、道具扣除、游戏结算、金币奖励、赠送金币、权限变更都使用服务端事务和幂等请求键，前端不能自行修改最终余额。

验收：两个浏览器登录不同账号时，一端完成结算/发送通知/修改权限后，另一端相关页面 3 秒内更新；刷新页面后数据不回退。

### 3.2 游戏完整状态

1. **游戏加载页。** 进入任意模式时预加载必要模型、纹理和音效；失败后给出“重试 / 返回大厅”，不能直接进入空白游戏画布。
2. **开始与退出。** 只有确认开始时才扣能量；退出确认框可继续游戏或退出。普通/困难主动退出按失败结算；无尽主动退出直接结算，不使用“失败”文案，结算返回大厅按钮居中。
3. **目标反馈。** 切水果显示分数、连击、汁液溅射和轻量停顿；炸弹有危险提示、爆炸闪光与短暂震动。特效不影响命中判定，也不因快速连续点击无限堆积。
4. **辅助与降级。** 无 WebGL、模型加载失败、低性能设备时显示明确降级说明，并保持 2D/临时几何体可玩；不允许空白页面或无响应点击。
5. **无尽规则可见。** 倒计时向上累计；显示本局基础分、综合评分和当前最高分。复活最多 3 次，其他道具单局最多 1 次；无尽没有下一关。

验收：网络慢、模型缺失、点击退出、能量不足、炸弹命中、连续切中、无尽结算六类情境均有明确结果且不重复扣资源。

### 3.3 账户、权限与安全底线

1. 注册与登录均需要协议勾选；用户名重复、密码不符合规则、协议未勾选给出就地错误提示。
2. 用户名只允许首次命名；再次修改时用不可关闭背景的说明弹窗解释规则，提供回到个人主页的单一操作。
3. 特殊权限授予与撤销必须重新输入管理员密码，并写入不可删除的审计日志。禁用玩家不出现在排行榜、权限候选和运营筛选中。
4. 内测账号的无限资源与任意关卡进入必须是服务端权限判定，普通用户篡改前端状态不得生效。
5. 登录令牌过期、异地登出和账户禁用需要统一跳回登录页，并说明原因；密码和令牌不能出现在日志或页面错误详情中。

验收：用浏览器开发工具修改余额、权限、关卡解锁状态后，提交业务请求仍被服务端拒绝；管理员操作能在日志中查到操作者、目标、时间与结果。

## 4. P1：显著提升留存与运营效率

### 4.1 玩家体验

- **大厅信息重排：** 上部只放玩家头像、等级/能量、金币和未读通知；中部突出“继续挑战”和三个模式；下部放活动、排行榜与历史战绩。避免把全部功能塞进首屏。
- **关卡卡片：** 已玩关卡显示最佳分、星级/通关状态、最近一次结果；困难模式只在边框和图标使用暗红风险提示，不用整块鲜红背景；无尽入口显示个人最高总分。
- **结算叙事：** 分数从基础分滚动到“综合评分”，再汇总总分；成功页面使用金色“通关”，普通失败页不混入成功按钮。
- **个人主页：** 头像、用户名、总金币、最高无尽分置于顶栏；下面用“最近战绩、常用道具、成就进度、账户设置”四个清晰区域，退出登录采用与主操作同尺寸的中号按钮。
- **商店与背包：** 商店首页仅显示商品图、价格与拥有状态；点击商品进抽屉/详情页后才看说明和数量选择。数量控件是黑底上下箭头，每次变化 1；购买按钮始终中等尺寸且等宽。
- **通知：** 未读有小红点；打开单条自动已读，已读卡片弱化但仍可查看；删除、全部已读和一键删除必须有撤销或二次确认，避免误删。

### 4.2 运营后台

- **玩家详情统一为审计视图：** 基本资料、当前余额、游戏记录、金币变动、道具消耗、充值记录、通知记录和管理员操作按时间线汇总。
- **筛选与分页：** 玩家、注册时间、日志时间支持模糊查询和自然分组；小跨度按天/周，大跨度按月/季/年。每页 5-8 条，分页按钮位置固定，首页/末页禁用。
- **商品与充值配置：** 商品表格占满横向区域，新增/编辑使用右侧抽屉；上传二维码可点击选择本地文件或拖入，保存后前台即时可见。二维码打开后 10 分钟自动关闭。
- **通知发布：** 支持全体和勾选玩家；发布前显示接收人数，发布后记录投递结果，不能因一个无效用户中止整批通知。
- **后台刷新：** 页面每 3-5 秒轻量刷新或使用实时事件增量更新。筛选、分页和正在编辑表单不应被自动刷新覆盖。

验收：管理员能在单一玩家详情中追踪一笔金币来源和去向；后台修改商品或发布通知后，前台无需手动刷新即可看到正确变化。

## 5. P2：体验加分项

- 音频设置：背景音乐、切割音、爆炸音独立开关和音量；遵守浏览器首次交互后才播放的限制。
- 触觉反馈：仅移动端、且用户主动开启后用于切中和炸弹；桌面不模拟震动。
- 新手引导：首次进入游戏仅提示“切水果、避炸弹、道具入口”，可以跳过，不做长篇教学。
- 成就与赛季：先定义服务端成就事件和赛季快照，再做展示；避免只做前端徽章。
- 可访问性：键盘焦点、屏幕阅读器标签、色盲不依赖单一颜色、最小触控面积和减少动态效果支持。

## 6. 需要先做的技术核查

| 项目 | 需要确认的事实 | 通过标准 |
| --- | --- | --- |
| 数据库迁移 | 表结构、索引和种子数据能否重复执行 | 全新数据库与已有数据库都能安全升级 |
| 事务与幂等 | 结算、资源扣除、购买、赠送与权限变更是否有唯一请求键 | 同一请求重复发送不重复扣款/加奖 |
| 实时连接 | 断线、重连、重复事件与乱序事件 | 页面不会回退到旧余额或旧通知状态 |
| 性能 | 低端手机、无 WebGL、模型与特效资源大小 | 画布非空、交互可用、无持续内存增长 |
| 审计 | 操作日志和账户消费日志的保留/删除策略 | 业务流水可追溯，临时状态可过期 |
| 支付边界 | 人工收款码的订单归属与超时 | 未支付不发货，超时二维码不可继续使用 |

## 7. 建议实施顺序

1. 建立 UI token：颜色、间距、圆角、按钮尺寸、文本层级、加载/错误/空状态组件。
2. 清除各页面剩余演示数据，完成 API 状态与实时更新的统一封装。
3. 整理大厅、关卡、个人页、商店、通知的布局与移动端适配。
4. 完成游戏加载、降级、退出、结算和特效的稳定性验收。
5. 完成后台玩家审计、商品配置、通知发布和安全确认流程。
6. 接入真实 GLB 水果，做模型加载、切半、爆炸、内存释放和低端设备性能测试。
7. 完成双账号联调、异常网络测试、权限回归和部署前检查。

## 8. 第二轮完成定义

以下条件同时满足才算第二轮完成：

- 主要页面在桌面与 390px 宽手机视口没有重叠、截断或按钮跳位。
- 所有业务页面从 API 读取真实数据，并具备加载、空、失败、重试状态。
- 资源变动和权限变动由服务端事务裁决，双账号同步正确。
- 游戏在有/无 3D 模型、能量不足、退出、炸弹、无尽结算下都有可理解且一致的交互结果。
- P0 自动化测试、关键 P1 接口测试、双账号手工回归和生产构建均通过。
- 管理员能追溯玩家的游戏、金币、道具、兑换、通知与权限操作；普通玩家无法看到或伪造这些数据。

## 9. 评审时需要决定的事项

1. 是否采用「午夜果园」为第二轮统一视觉方向。
2. 第二轮是否只翻新玩家端，还是玩家端与后台一起统一。
3. 充值是否继续保持人工收款码展示，还是在部署后接入第三方支付。
4. 成就/赛季是否进入第二轮，或留到第三轮。
5. 真实水果 GLB 的来源、授权证明、单个文件大小上限与目标设备性能线。
