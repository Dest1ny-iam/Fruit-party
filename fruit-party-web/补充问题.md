## 实际限制与后续事项

### 1. 浏览器命中数据仍不是完全防作弊

当前服务端会锁定场次、忽略客户端传来的倍率、限制道具与复活，但水果命中仍由浏览器上传。真正的竞技防作弊需要服务端模拟游戏，或把每次输入事件带时间戳、随机种子和签名后再校验。这是架构升级，不适合在当前 Three.js 浏览器游戏上伪装成已完成。

### 2. 支付平台真实回调尚未接入

已具备管理员确认到账的完整运营闭环。接入微信支付、支付宝等真实支付时，需要按其官方协议验证签名、金额、订单号和回调幂等键，不能把普通 HTTP 请求直接当作支付成功。

### 3. 限流在多实例部署时应切到 Redis

当前限流保存在 Node 进程内存，单台 API 足够使用。PM2 cluster 或多台服务器时，每个进程各有一份计数，需改为 Redis 共享计数器，Nginx 也应提供第一层限流。

### 4. 图片上传仍是 data URL 方案

现有前端把二维码图片转换为 data URL，后端校验 MIME 前缀与长度。生产环境应改成独立上传接口，在服务器用图片解析库核验真实格式、像素和文件大小，再保存至对象存储。

### 5. 数据库迁移需要版本化

当前 schema 会在启动时补建表，适合开发和小规模部署。正式上线前应建立 `schema_migrations` 表，按版本执行不可变 SQL 文件，并在发布前备份数据库。

### 6. 监控与告警需要部署时配置

代码可通过 PM2 保持运行，但日志轮转、错误告警、慢查询监控、备份任务和 HTTPS 证书续期由部署环境配置。具体操作见桌面的学习手册和部署章节。

### 本轮修复的问题

收入统计曾把一笔已支付订单显示为 0。根因是 MySQL `DATETIME` 在 Node 中转为 UTC 后跨了日期边界。现已改为 MySQL 直接返回 `YYYY-MM-DD` 的支付日期，再按数据库日期统计。对应回归测试已经通过。

双账号联调脚本也同步到游戏场次机制：先调用开局接口取得 `sessionId`，再提交结算。禁用检查改为权限中心候选接口，因为玩家管理列表本来需要保留禁用账号以便管理员恢复账号。
