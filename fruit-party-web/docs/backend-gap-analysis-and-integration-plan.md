# 水果派对：后端业务与前后端联调查缺补漏方案

> 文档版本：2026-09-29
> 适用分支：`codex/iteration-one`
> 数据库约束：MySQL 是唯一业务数据库，前端不得保存业务演示数据。

## 1. 文档目的

这份文档用于上线前检查当前项目还缺少什么、哪些功能已经完成、后续应该按什么顺序补齐。重点不是重新设计 UI，而是保证：

1. 游戏分数、能量、金币、道具、关卡和权限由服务端事务控制。
2. 前端只展示 API/SSE 返回的数据，不使用业务虚拟数据。
3. 重复请求、并发请求、刷新页面和网络重试不会造成重复扣费、重复发奖或越权。
4. 充值、维护、账号禁用和后台运营功能具备完整闭环。

## 3. 必须优先完成的 P0 项

### 3.1 服务端游戏 session 与结算幂等

#### 当前问题

开局接口已经创建 `game_sessions`，但前端结算请求没有提交 `sessionId`，服务端结算也没有读取并锁定该 session。客户端仍可以重复提交一组命中数据。

#### 目标行为

- 开局返回 `sessionId`、模式、关卡、开始时间和本局允许的道具。
- 结算必须携带 `sessionId`。
- 事务中执行：锁定 session → 校验用户、模式、关卡和状态 → 计算结算 → 写入 attempt → 发奖/更新进度 → 将 session 标记为 `settled`。
- 同一 session 二次结算返回第一次结算结果，不重复发金币、不重复解锁。
- 非法 session、跨用户 session、模式/关卡不匹配统一返回明确错误。
- 维护或异常退出时可把 active session 标记为 `abandoned`，不能再次领奖。

#### 建议接口

```text
POST /api/game/entries
  response: { sessionId, mode, levelNumber, startedAt, activeItems }

POST /api/game/settlements
  body: { sessionId, fruitHits, hitRate, elapsedSeconds }
  response: { settlement, replayed }
```

#### 验收测试

1. 同一 `sessionId` 连续提交两次：第二次不新增金币流水。
2. A 用户使用 B 用户的 `sessionId`：返回 403。
3. normal 第 1 关的 session 提交 hard 第 1 关：返回 409/422，不写 attempt。
4. 两个并发请求结算同一 session：只能产生一条 attempt 和一条金币流水。
5. 已结算 session 再提交：返回原结算结果，`replayed=true`。

### 3.2 无尽模式道具服务端校验

#### 当前问题

无尽模式的炸弹削减、20 秒分数倍率和复活次数主要由 `GameBoard.vue` 保存。客户端可以修改倒计时、命中记录或 `scoreBoost` 字段。

#### 目标行为

- 服务端 session 保存本局道具状态、已使用次数和效果起止时间。
- 无尽单局复活最多 3 次；普通/困难按规则最多 1 次。
- 每种主动道具单局最多使用 1 次。
- 服务端结算只接受服务端认可的效果状态，不信任客户端传来的倍率字段。
- 复活必须携带 sessionId，并在事务中锁定库存和 session。

#### 建议数据结构

可在 `game_sessions` 增加 JSON 状态字段，或增加独立表：

```text
game_session_items
  session_id, item_key, uses_allowed, uses_used,
  active_from, active_until
```

独立表更容易审计和并发锁定；推荐独立表。

### 3.3 充值支付到账闭环

#### 当前问题

目前可以创建待支付订单并显示二维码，但没有把订单推进到 `paid`，也没有根据商品权益发放金币、能量或道具。

#### 目标流程

```text
创建订单 pending
    ↓
支付平台回调 / 管理员确认
    ↓
事务锁定订单
    ↓
校验金额、订单状态和回调幂等键
    ↓
写支付记录 + 发放权益 + wallet/inventory 流水
    ↓
订单改为 paid，广播 player-state
```

#### 必须提供的接口

```text
POST /api/recharge-orders
GET  /api/recharge-orders/:orderNo
POST /api/admin/recharge-orders/:orderNo/confirm
POST /api/payments/callback       # 接入真实支付平台时使用
```

管理员确认接口必须记录管理员、确认时间、确认金额和操作审计。订单已经是 `paid` 时重复确认必须返回原结果，不能重复发放。

#### 订单状态规则

| 状态 | 可转移到 | 说明 |
| --- | --- | --- |
| pending | paid / expired / cancelled | 待支付 |
| paid | 无 | 已发放权益，不允许回退 |
| expired | 无 | 超时订单不可确认 |
| cancelled | 无 | 主动取消 |

### 3.4 维护状态改为 MySQL + 实时同步

#### 当前问题

`App.vue` 中维护状态是内存变量，项目还保留 `localStorage` 状态模块。多浏览器、多进程下会不一致。

#### 目标行为

- 新增 `system_settings` 表，保存维护开关、公告、更新时间和操作者。
- 后台开启/结束维护调用 API，事务写库并写审计。
- SSE 广播 `maintenance-changed`。
- 维护开启后：禁止新开局；已进行中的对局允许完成，或显示维护倒计时后安全结算。
- 登录页/大厅显示维护公告，不能只依赖浏览器缓存。

## 4. 必须补齐的 P1 业务

### 4.1 主页金币流水

当前 `App.vue` 将 `coin-ledger` 固定传为 `[]`，需要改为真实接口：

```text
GET /api/me/wallet/ledger?page=1&pageSize=20
```

返回游戏奖励、商城消费、管理员赠送、充值发放等流水。每条记录至少包含：

```json
{
  "id": 12,
  "title": "完成普通模式第 1 关",
  "amount": 120,
  "balanceAfter": 620,
  "occurredAt": "2026-09-29T12:00:00.000Z"
}
```

### 4.2 后台道具完整 CRUD

目前只有价格修改接口。建议补齐：

```text
GET   /api/admin/items?page=1&pageSize=20&keyword=
POST  /api/admin/items
PATCH /api/admin/items/:itemId
PATCH /api/admin/items/:itemId/status
```

字段包括 `itemKey`、名称、说明、图标、价格、最大购买数量、排序和启用状态。新增道具后，玩家端商店接口自动返回，分页由服务端负责。

### 4.3 后台列表统一分页和刷新

玩家、道具、充值商品、通知、审计日志都应返回：

```json
{ "items": [], "page": 1, "pageSize": 20, "total": 0 }
```

后台可采用 10～15 秒轮询作为基础保障，再用 SSE 做即时刷新通知。刷新失败时保留旧数据并显示错误状态，不能把页面误显示成空列表。

### 4.4 权限中心完善

权限操作必须区分“授予”和“撤销”的颜色、文案和审计动作。建议权限字段统一为：

```text
infiniteEnergy
infiniteCoins
unlockAllLevels
testerMode
```

每次变更都要记录管理员、目标玩家、变更前值、变更后值、IP/请求编号和时间。已禁用玩家不能出现在权限中心，也不能被授予权限。

## 5. P2 安全与工程补充

### 5.1 认证安全

- 生产环境禁止使用默认 JWT 密钥；启动时没有 `JWT_SECRET` 应直接失败。
- 登录、注册、管理员敏感操作增加 IP/账号限流。
- 连续失败登录触发短暂锁定或退避。
- CORS 只允许配置的前端域名，不使用无条件 `cors()`。
- Cookie 生产环境启用 `secure`、`httpOnly`、`sameSite`。

### 5.2 文件上传安全

- 收款码和头像限制 MIME、扩展名、文件大小。
- 不信任客户端文件名。
- 生产环境保存到对象存储或受控目录，不直接把任意路径写入数据库。
- 图片上传失败时不修改原有头像/收款码。

### 5.3 数据库和部署

- 使用版本化迁移，而不是只在启动时执行整份 schema。
- 增加 MySQL 备份、恢复和迁移回滚文档。
- 提供 PM2/Docker/Nginx 配置，API 与前端静态资源分开部署。
- 配置日志轮转、错误告警、慢查询监控和连接池指标。
- 生产数据库禁止使用测试种子账号密码。

## 6. 前后端联调测试矩阵

### 6.1 正常流程

1. 注册新账号，勾选协议，成功进入大厅。
2. 登录 tester，确认内测开关、无限能量、无限金币和关卡权限生效。
3. 普通用户开始第 1 关，能量扣 1，完成后下一关解锁。
4. 商城购买道具，金币扣减、库存增加、流水写入。
5. 使用能量卡：满能量返回 `ENERGY_FULL`；非满能量恢复 1 格并正确处理倒计时。
6. 无尽模式退出：只结算，不显示成功/失败，不出现下一关。
7. 管理员给玩家赠送 1000 金币：重复点击同一操作编号只能到账一次。
8. 管理员发布全体通知和勾选通知，目标玩家实时收到。

### 6.2 异常和边界流程

| 场景 | 预期 |
| --- | --- |
| 密码缺少大写字母/数字 | 422，明确提示密码规则 |
| 用户名重复 | 409，提示用户名已被注册 |
| 负数价格、数量、关卡 | 422，不写数据库 |
| 禁用账号登录 | 403，弹出封禁提示 |
| 两个并发购买请求 | 余额不会变负，库存和流水一致 |
| 两个并发结算请求 | 只生成一条 attempt 和一条奖励流水 |
| 过期充值订单确认 | 拒绝发放权益 |
| 已支付订单重复确认 | 返回原结果，不重复发放 |
| 管理员错误密码授权 | 401，不改变权限 |
| 越权读取其他玩家数据 | 403/404，不泄露数据 |
| SSE 断线 | 自动重连或显示最后一次已知状态，不清空页面 |

### 6.3 压力与并发建议

- 购买接口：100 个并发请求，验证余额、库存、流水三者总量一致。
- 结算接口：同一 session 50 个并发请求，必须只有一个有效写入。
- 排行榜：持续读取时同时写入结算，不能出现 SQL 错误或脏数据。
- SSE：至少 20 个客户端同时连接，管理员操作后所有目标客户端收到更新。
- 连接池耗尽时请求应排队或快速失败，不能创建无限连接。

## 7. 推荐实施顺序

### 阶段 A：可信游戏业务

1. 结算请求加入 `sessionId`。
2. session 锁定、状态机和重复结算返回。
3. 复活和无尽道具状态迁移到服务端。
4. 增加并发结算测试。

### 阶段 B：充值和运营闭环

1. 订单查询、管理员确认、支付回调接口。
2. 权益发放事务和幂等键。
3. 维护状态表、后台开关和 SSE。
4. 后台玩家/道具/通知统一分页和刷新。

### 阶段 C：数据完整性与上线安全

1. 接入主页金币流水。
2. 清理仍被引用的本地演示 store。
3. 完成认证限流、上传校验和生产密钥检查。
4. 补齐 Docker/PM2/Nginx、备份和迁移文档。
5. 补齐剩余水果 GLB 并完成切半验收。

## 8. 上线前最终验收清单

- [ ] 所有玩家页面数据都来自 MySQL API/SSE。
- [ ] 项目中没有生产路径使用本地 fixture、演示 store 或固定空数组。
- [ ] 每次游戏结算都绑定唯一 session，重复请求不会重复奖励。
- [ ] 能量、金币、道具和关卡更新都在事务中完成。
- [ ] 充值订单能从 pending 正确走到 paid，并且幂等发放权益。
- [ ] 维护状态在多浏览器、多进程中一致。
- [ ] 禁用账号不能登录、上榜、进入权限中心或接受运营操作。
- [ ] 后台列表全部支持服务端分页和失败重试。
- [ ] JWT、CORS、限流、上传、日志和备份已配置生产策略。
- [ ] `npm test`、`npm run build`、MySQL 集成测试、并发测试全部通过。

## 9. 当前结论

项目已经完成了较多基础业务和 MySQL 迁移工作，但仍处于“可继续联调、不可直接正式部署”的状态。最影响可靠性的三个缺口是：

1. 结算没有完全绑定服务端 session。
2. 充值没有支付到账闭环。
3. 主页流水和维护状态仍未完全接入真实后端。

完成阶段 A 和阶段 B 后，核心业务才具备上线验收条件；完成阶段 C 后，才适合进入正式部署准备。
